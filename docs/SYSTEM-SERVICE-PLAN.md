# תכנון: רכיב שירות ברמת SYSTEM להקשחת הנעילה

מסמך תכנון (לא קוד) לשדרוג הארכיטקטוני הגדול ביותר שנדרש כדי לחזק את מצב הנעילה. נכתב בהמשך ל-#1 ו-#2.

> הבהרה מקדימה: גם שירות SYSTEM **אינו** יכול לקבוע סיסמת BIOS/UEFI או לחסום אתחול מ-USB — אלו הגדרות firmware שנעשות ידנית בכל מחשב. המסמך הזה עוסק רק במה שאפשר להקשיח בתוך Windows.

## הבעיה
כיום הגשר (`OtzariaBridge.exe`) רץ **בהרשאות המשתמש המחובר**. לכן:

1. כל מדיניות שהוא כותב היא תחת `HKCU` — והמשתמש עצמו יכול לבטל אותה.
2. `kiosk.active` וגיבוב הסיסמה יושבים ב-`%LOCALAPPDATA%\OtzariaBridge\config.json`, שהמשתמש יכול לקרוא, למחוק או לדרוס (ראו ה-PR להגנת `EnsureNotProtected` — הוא סוגר את הערוץ דרך הגשר, אבל לא דרך סייר חיצוני/שורת פקודה).
3. אין הגנה מול **חשבון Windows שני** או מול משתמש עם הרשאות מנהל.
4. אין אכיפה שעולה לפני הכניסה (pre-logon).

כלומר הנעילה היא "רכה" מיסודה. כדי להפוך אותה ל"קשה" צריך רכיב שרץ מחוץ להישג ידו של המשתמש הנעול.

## ארכיטקטורה מוצעת

שני תהליכים במקום אחד:

| רכיב | הרשאות | תפקיד |
|---|---|---|
| **OtzariaBridgeService** (חדש) | LocalSystem, Windows Service | מקור האמת לנעילה; אוכף מדיניות; watchdog; מחזיק את הסוד |
| **OtzariaBridge** (קיים) | המשתמש המחובר | שרת ה-HTTP לתוספים + אייקון מגש; **מבקש** פעולות מהשירות |

### תקשורת
Named Pipe מקומי (`\\.\pipe\OtzariaBridge`) עם ACL שמתיר רק `Authenticated Users` לכתוב ו-`SYSTEM` לקרוא. כל בקשה משנת־מצב (enable/disable/set-password/settings) מועברת מהגשר אל השירות; השירות מאמת סיסמה ומבצע. בקשות קריאה (status) יכולות להישאר בגשר.

### מקום הסוד
גיבוב הסיסמה וקוד השחזור עוברים מ-`config.json` של המשתמש אל:
- `HKLM\SOFTWARE\OtzariaBridge` **או** `%ProgramData%\OtzariaBridge\config.json`
- עם ACL שמתיר כתיבה ל-SYSTEM/Administrators בלבד, וקריאה בלבד למשתמשים.

כך משתמש נעול לא יכול לאפס את הנעילה בעריכת קובץ.

## יכולות שהשירות מאפשר (שלא ניתנות היום)

1. **מדיניות ב-HKLM שהמשתמש לא יכול לבטל** — `DisableTaskMgr`, `NoClose`, הגבלת הרצת תוכנות (עדיף **AppLocker/WDAC** ולא GPEDIT לפי שם קובץ, שפריץ).
2. **Watchdog שמחזיר מדיניות שהוסרה** — השירות בודק מחזורית ומשחזר ערכים שנמחקו.
3. **הגנה מול חשבון שני** — זיהוי חשבונות משתמש נוספים והחלת הנעילה גם עליהם, או חסימת כניסה לחשבונות לא־מאושרים (שקול: שינוי הרשאות/`net user`).
4. **חסימת כונני USB אחסון** — דרך מדיניות התקנים (`USBSTOR Start=4`) או חסימת התקנה של התקני אחסון חדשים. דורש הרשאות מנהל; חסימה מלאה ברמת דרייבר היא מעבר לכך.
5. **הקשחת אתחול** — ר' `BOOT_HARDENING.md`.
6. **אכיפה שעולה עם המערכת** — השירות רץ עוד לפני הכניסה, כך שהנעילה חלה גם אם הגשר של המשתמש עדיין לא עלה.

## התקנה והסרה
- **התקנה** דורשת הרשאות מנהל פעם אחת (`sc create` / `ServiceInstaller`). אם אין הרשאות — נ fallback לנעילה הרכה הקיימת, עם אזהרה (כבר קיים זיהוי חשבון מנהל ב-PR האזהרות).
- **הסרה** דורשת את סיסמת הנעילה (כמו `--uninstall --password` הקיים), ומסירה את השירות, המדיניות וה-ACL.

## סיכונים ושיקולים
- **אנטי-וירוס / SmartScreen**: שירות SYSTEM שכותב מדיניות, חוסם USB ומתקין keyboard hook — דפוס שמנועי הגנה עלולים לסמן. **חתימת קוד** (שחסרה היום) הופכת לחובה.
- **נעילה שמנעה גישה לגיטימית**: watchdog אגרסיבי עלול לנעול את המחשב גם מהמנהל. חובה נתיב חירום ברור (קוד שחזור שעובד ברמת השירות, ו-Safe Mode כרשת ביטחון).
- **מורכבות**: זה שינוי מהותי (service lifecycle, IPC, ACLs, הגירת config). עדיף בשלבים.

## תוכנית בשלבים
1. **שלב 0 (בוצע/בתהליך):** הקשחות ברמת המשתמש — `EnsureNotProtected` לכתיבה, חסימת רשת בנעילה, מצב קריאה-בלבד, אזהרות מצב חלש.
2. **שלב 1:** שירות מינימלי שמחזיק את הסוד ואת `kiosk.active` ב-HKLM, עם named pipe ל-enable/disable/verify. הגשר הופך ל-proxy.
3. **שלב 2:** watchdog של מדיניות ב-HKLM + אכיפה pre-logon.
